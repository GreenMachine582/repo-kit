# 🤝 Contributing

repo-kit uses its own `dev-main` profile, the same branch model it generates for every repo.

## 🔀 Flow

```
branch ──► commits ──► draft PR to dev ──► ready ──► checks pass ──► merge commit ──► dev
                                                                                       │
              tag vX.Y.Z ◄── release PR merged ◄── dev → main PR ◄────────────────────┘
                  │
                  └──► main merged back into dev
```

- `dev` is the default branch and the base for feature PRs. `main` only receives release PRs from `dev`.
- Neither `dev` nor `main` takes a direct push. Changes go through a PR, merged with a **merge commit**.
- A PR's base can also be another feature branch, to chain PRs. When the parent merges, the child is retargeted.
- Open PRs as drafts. Mark them ready when done: only ready PRs are kept current by the PR bot. Add `wip` to a ready
  PR under rework.
- Update an open PR by adding commits, or by merging its base in (`rk wt sync`). Never rebase and force-push.
- One change per PR. Code and the docs that describe it go in the same PR.

**Branch names:** `<type>/<short-description>`, such as `feat/worktree-start` or `docs/adoption`.

## ✍️ Commit messages

[Conventional Commits](https://www.conventionalcommits.org), with a first line of at most 100 characters and a body
explaining why. Every commit in a PR is checked by `commits`; merge commits are skipped.

| type | for |
|---|---|
| `feat` | new behaviour |
| `fix` | something that was broken |
| `docs` | documentation only |
| `chore` | housekeeping that changes no behaviour |
| `refactor` | restructuring with the same behaviour |
| `test` | tests only |
| `ci` | GitHub Actions workflows |
| `build` | tooling and dependencies |
| `perf` | faster or lighter, same behaviour |
| `revert` | undoing an earlier commit |

A breaking change is `feat!:` (or a `BREAKING CHANGE:` footer), with migration notes that `rk upgrade` prints.

## 🏷️ PR titles

PR titles are **not** Conventional Commits: write a plain sentence, such as `Add worktree commands`. With merge commits,
every commit already reaches the changelog, so a conventional title would add a duplicate line. `pr-title` enforces
this. Release PRs (`release: …`, `chore(main): release …`) are allowed.

## 🚢 Releasing

release-please keeps a release PR open, with the version bump and changelog worked out from the commits. Merging it
tags `vX.Y.Z` and publishes the GitHub Release, then `main` is merged back into `dev`. Never bump versions or edit
released changelog sections by hand, and never move a `v*` tag: consumers pin exact tags, and there is no floating
`v1`.

Release PRs are opened with a token from the `gth-release-bot` GitHub App, so they trigger CI. Setup is in
[docs/github-app.md](docs/github-app.md).

## 🔒 Rules

Rulesets and repo settings are generated by `rk github` from the `dev-main` profile (see
[docs/rulesets.md](docs/rulesets.md)): a PR and green required checks for `dev` and `main`, no force-pushes or
deletion, and `v*` tags created only by `gth-release-bot`. An admin can merge past failing checks; it is logged.

Until Phase 1D lands, `.github/workflows/ci.yml` is written by hand and the rules are set by hand.
